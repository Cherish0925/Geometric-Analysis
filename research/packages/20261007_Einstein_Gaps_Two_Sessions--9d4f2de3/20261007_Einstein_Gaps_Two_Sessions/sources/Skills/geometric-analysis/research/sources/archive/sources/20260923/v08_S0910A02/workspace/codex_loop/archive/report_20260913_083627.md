# Research Report: Lean curvature interface for Yau Problem 26

## Task and outcome

This run audited the locked Lean/Mathlib environment for the geometric objects needed to state Yau Problem 26: closed smooth real manifolds, smooth Riemannian metrics, Levi--Civita connections, Riemann and Ricci curvature, quadratic-form pinching, and an Einstein-metric conclusion.

The decisive result is that Mathlib v4.33.1 has a genuine lower-level connection stack but no curvature stack. Smooth Riemannian bundle metrics, bundled covariant derivatives, smoothness of connections, torsion, and metric compatibility are present. There is no geometric Levi--Civita constructor or existence/uniqueness theorem, no Riemann tensor, no Ricci contraction, and no scalar or sectional curvature. Therefore a faithful, unconditional Yau 26 statement cannot yet be written solely with canonical Mathlib notions. The Step 71 synthetic statement remains non-faithful and should not be used as a geometry result.

I produced a compiling interface prototype that exposes the missing construction rather than hiding it behind an uninterpreted Ricci predicate. It is a specification for future library work, not a formalization or proof of Yau 26.

## Evidence and real APIs found

The audit used Lean 4.33.1 and locked Mathlib input `v4.33.1`, Git revision `0df444a360eaa60ab8c11dca51a86af692955474`. Three independent checks agreed:

- A reproducible scan of all 8,311 locked Mathlib `.lean` sources found zero matches for Levi--Civita, Christoffel, Riemann curvature/tensor, Ricci, scalar curvature, and sectional curvature. The one generic occurrence of “curvature” is prose about a hyperbolic disc in a measure-theory comment.
- A Lean environment scan over every constant loaded by `import Mathlib` found zero declarations under the tested curvature spellings, while finding 163 `CovariantDerivative` and 100 `RiemannianMetric` substring hits. This confirms both the missing high-level layer and the presence of the new substrate.
- A direct declaration probe compiled the exact relevant types and predicates.

The usable Mathlib boundary is:

- `Bundle.ContMDiffRiemannianMetric`, `.toRiemannianMetric`, `Bundle.RiemannianBundle`, and `IsContMDiffRiemannianBundle` for smooth positive-definite bundle metrics;
- `CovariantDerivative` and `CovariantDerivative.ContMDiffCovariantDerivative` for bundled smooth connections;
- `CovariantDerivative.torsion` and `.torsion_eq_zero_iff` for torsion;
- `CovariantDerivative.derivMetricTensor` and `.IsMetricCompatible` for metric compatibility;
- `LinearMap.trace` for the algebraic Ricci contraction once a curvature endomorphism exists;
- `LinearMap.BilinForm.IsNonneg` and `.IsPosSemidef` for algebraic quadratic-form positivity;
- `IsManifold (𝓡 n) ∞ M`, `T2Space`, `SecondCountableTopology`, `CompactSpace`, and `ConnectedSpace` for a standard closed connected smooth real-manifold context. The model `𝓡 n` is boundaryless. `IsRiemannianManifold` and `EMetricSpace.ofRiemannianMetric` also exist, but concern the path-length metric and do not provide curvature.

The Mathlib connection files themselves describe unfinished foundations: dependence of a covariant derivative on the section's 1-jet is still planned, as are induced Hom-bundle connections and parallel transport. This helps explain why the curvature layer has not yet been built.

## Prototype produced

`Sessions/S0910A02/workspace/codex_loop/work/lean_curvature_interface_step73/CurvatureInterfacePrototype.lean` uses actual Mathlib types for the manifold, tangent bundle, smooth metric, smooth vector fields, connection, connection smoothness, torsion, metric compatibility, and trace.

Its central `GeometryFor g` structure is the explicit gap. It requires:

- a smooth tangent connection;
- the real Mathlib laws `torsion = 0` and `IsMetricCompatible` for the supplied metric;
- a pointwise continuous trilinear tensor `R(X,Y)Z`;
- a realization law equating that tensor on smooth vector fields to `∇_X ∇_Y Z - ∇_Y ∇_X Z - ∇_[X,Y] Z`.

The prototype then defines, rather than assumes,

`Ric(v,w) = trace (z ↦ R(z,v)w)`.

It expresses `c g ≤ Ric ≤ C g` literally as the two diagonal inequalities for every point and tangent vector, and defines an Einstein metric by a single global `λ : ℝ` satisfying `Ric_h = λ h` on all tangent-vector pairs. The global design quantifies compactness, connectedness, Hausdorffness, second countability, smoothness, and the boundaryless `n`-dimensional real model explicitly.

The remaining `CurvatureAPI` field asks for this geometry for every smooth metric. Its required nonemptiness is deliberately visible in `DimensionStatementDesign`; that makes the file honest about the missing Mathlib construction, but also means the definition is not yet the mathematical Yau 26 statement.

## Unresolved work and recommendation

The next honest step is to build a small Mathlib curvature library, in this order:

1. Define the connection commutator and prove pointwise tensoriality, packaging it as a `(1,3)` curvature tensor. The pending 1-jet result in the connection API may be a prerequisite or may need a local workaround.
2. Construct and prove uniqueness of the Levi--Civita connection associated to `Bundle.ContMDiffRiemannianMetric`, including smoothness, zero torsion, and metric compatibility.
3. Define Ricci by `LinearMap.trace`; prove bilinearity, smoothness, and symmetry for Levi--Civita curvature.
4. Package a pointwise order on symmetric bilinear-form fields using nonnegativity of the difference, and connect it to the diagonal inequalities used here.
5. Replace the prototype `CurvatureAPI` by the canonical constructions. Only then rewrite `DimensionStatementDesign` as a faithful unconditional Yau 26 statement. Scalar and sectional curvature can follow later because they are not required merely to state the Ricci-pinching problem.

Qiushi should use the prototype as a type-correct specification and regression test for that library effort. It should not cite the prototype or its audited logical lemma as progress on proving Yau 26 itself.
